# 第二版并行开发分工与合并规则

更新时间：2026-10-05

当前执行方式：用户已决定停止并行工作区，后续全部功能在主项目 `D:\页面编辑器` 按工作流 1 → 2 → 3 顺序完成。本文件保留并行分工内容，作为第二版交付范围和模块边界参考。

## 当前判断

第二版 A 阶段已经完成第一批动态元素编辑实现，但还需要在 `D:\test` 完成动态标题、声音图片按钮、图片、背景图和容器的实际界面验收。第二版 B、C、D 尚未完成。

三个聊天可以并行开发，但不能直接共用同一个工作目录。当前项目尚未建立 Git 工作区隔离，因此并行前必须先建立基线提交，再为每个工作流建立独立分支或独立工作区。

## 三个工作流

### 工作流 1：动态编辑收尾与基础交互（A 收尾 + B）

负责内容：

- 完成真实 Vue/React/原生 JavaScript 项目的动态元素验收。
- 完善动态标题、图片按钮、声音按钮、卡片、容器、背景图的文字、样式、位置和素材保存。
- 支持页面跳转、返回、显示/隐藏、弹窗、样式切换、音视频播放/暂停等基础交互。
- 保证编辑模式不会误触发网页交互，测试模式能运行原有逻辑。
- 保证当前页面、下一页、返回和弹窗状态在刷新后仍对应正确页面。

工作流 1 的交付标准：

1. 在真实项目中修改动态标题、声音按钮、图片按钮和卡片，保存后刷新仍然存在。
2. 同一个动态按钮至少连续拖动并保存两次，第二次保存不能报找不到元素。
3. 完成一个页面跳转、一个显示/隐藏、一个弹窗和一个媒体控制案例。
4. 编辑模式点击只用于选中和拖动，测试模式点击才执行网页交互。
5. 运行 `npm run typecheck`、`npm run build` 和主进程语法检查通过。

建议新增或维护的目录：

- `src/interaction/`
- `src/preview/`
- `electron/preview/`
- `examples/interaction-fixtures/`

工作流 1 不负责版本历史和 AI API。

### 工作流 2：完整版本历史（C）

负责内容：

- 将 HTML、CSS、JS 和素材替换纳入同一个版本记录。
- 版本名称、时间、修改说明和涉及文件展示。
- 支持单文件恢复和一次完整修改恢复。
- 恢复前自动创建当前快照。
- 支持删除过期快照，删除必须二次确认。
- 恢复失败时保留当前项目可用。

工作流 2 的交付标准：

1. 修改 HTML、CSS、JS 和图片后生成一个完整版本。
2. 能查看版本内容和涉及文件。
3. 能恢复单个文件，也能恢复一次完整修改。
4. 至少完成 3 次版本恢复，恢复后页面可正常加载。
5. 删除快照有二次确认，取消删除不会改变文件。

建议新增或维护的目录：

- `electron/version-store.cjs`
- `src/version/`
- `docs/version-history.md`

工作流 2 不负责动态元素选择和 AI 请求，只提供稳定的快照、差异和恢复接口。

### 工作流 3：用户 API 的 AI 代码助手（D）

负责内容：

- API 地址、模型和密钥配置。
- 支持 OpenAI 兼容的 Chat Completions 或 Responses 格式。
- 当前页面相关代码上下文选择。
- AI 修改说明、受影响文件和代码差异预览。
- 隔离预览、运行检查、用户确认后应用。
- 用户拒绝不改文件，生成失败自动回滚。
- AI 主要处理答题判断、计分、分支跳转、状态保存、弹窗和媒体控制等复杂 JavaScript 逻辑。

工作流 3 的交付标准：

1. 未配置 API 时，普通编辑器仍然可用。
2. 密钥不写入项目、HTML、CSS、JS、localStorage 或普通日志。
3. AI 修改在确认前不能写入项目文件。
4. 能完成一次“点击按钮判断选项并显示反馈”的生成、差异预览和确认应用。
5. 至少完成一次拒绝、一次确认应用和一次失败回滚。
6. AI 生成的代码在隔离预览中运行失败时，项目恢复到修改前状态。

建议新增或维护的目录：

- `electron/ai/`
- `src/ai/`
- `src/ai-api/`
- `docs/ai-implementation.md`

工作流 3 依赖工作流 2 提供的快照和恢复接口。AI 可以先用 `SnapshotService` 接口和假实现开发，等工作流 2 合并后再接入真实实现。

## 文件冲突规则

三个聊天不能同时直接修改以下共享文件：

- `src/App.tsx`
- `src/styles.css`
- `src/electron.d.ts`
- `electron/main.cjs`
- `electron/preload.cjs`
- `package.json`

功能聊天应把新逻辑放在自己的目录，并提供明确的接口和集成说明。由最后的集成工作流统一修改共享文件、注册 IPC、接入菜单和运行回归。这样可以避免一个聊天覆盖另一个聊天的改动。

每个工作流完成时必须提交：

1. 修改文件清单。
2. 已完成和未完成的功能清单。
3. 可重复的验收步骤。
4. `npm run typecheck`、`npm run build` 和专项测试结果。
5. 与其他工作流需要的接口说明。

## 依赖与合并顺序

```text
第一版稳定基线
       ├── 工作流 1：A 收尾 + B ──┐
       └── 工作流 2：C ────────────┼── 最后集成与完整回归
                    工作流 3：D ──┘
```

工作流 1 和工作流 2 可以同时开发。工作流 3 可以先使用快照接口假实现开发，但正式合并必须在工作流 2 的恢复接口通过后进行。最终合并顺序为：工作流 1 → 工作流 2 → 工作流 3 → 全量验收。

## 并行聊天启动提示

工作流 1：

> 你负责第二版工作流 1：动态元素收尾与基础交互。只处理动态元素保存、页面跳转、返回、显示隐藏、弹窗、样式切换和媒体控制。不要实现版本历史和 AI。请在独立工作区中开发，完成后给出修改文件、测试命令和验收步骤。

工作流 2：

> 你负责第二版工作流 2：完整版本历史。只处理 HTML、CSS、JS、素材的快照、差异、命名版本、恢复和删除确认。不要修改动态选择和 AI 逻辑。请提供稳定的 SnapshotService 接口和专项测试，在独立工作区中开发。

工作流 3：

> 你负责第二版工作流 3：用户自带 API 的 AI 代码助手。只处理 API 配置、密钥安全、上下文选择、差异预览、隔离运行、确认应用和失败回滚。先依赖 SnapshotService 接口假实现，不要直接覆盖项目文件，不要修改基础拖拽逻辑。请在独立工作区中开发并提供专项测试。

## 最终第二版交付门槛

三个工作流合并后，必须重新执行 [09-version-2-scope-and-acceptance.md](./09-version-2-scope-and-acceptance.md) 的全部交付条件，包括真实动态项目验收、10 次交互修改、10 次撤销/重做、3 次版本恢复、AI 拒绝/确认/失败回滚，以及构建和安全检查。
