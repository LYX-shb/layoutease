# 代码结构审查与分步修改计划

审查日期：2026-11-01。基线：`v0.1.10` / `c47e5f0`。

本次检查目录划分、关键文件职责、消息接口、保存路径、依赖配置与测试组织，采用源码静态审查。未重新运行应用、测试或打包；历史测试结果见版本记录。本页给出修改计划，运行代码尚未按此计划重构。

## 总体判断

仓库已经具备桌面应用、界面、测试、示例与文档的基础分层，也把播放暂停、布局范围和图片替换等逻辑拆成了模块。当前主要问题是主入口仍承担过多职责、通用编辑与特定项目适配混合，以及缺少可自动执行的工程约束。

建议沿用 Electron、React、TypeScript 和现有保存格式，逐批收拢边界。优先处理文件保存一致性和通信约束，再拆分大文件；每批保持现有安装包和旧项目可继续使用。

## 已有基础

- `src/`、`electron/`、`tests/`、`scripts/`、`examples/`、`docs/` 的顶层用途清楚。
- 界面 TypeScript 开启 `strict`，仓库包含依赖锁文件。
- 桌面窗口已开启 `contextIsolation`、关闭 `nodeIntegration` 并启用 `sandbox`，见 [窗口创建](../electron/main.cjs#L2291)。
- 界面接收预览消息时检查 `event.source` 是否为当前 iframe，见 [预览消息处理](../src/App.tsx#L423)。
- 保存前创建项目快照，AI 修改具备隔离预览与失败恢复流程。
- 已有编辑范围、SVG 选择与缩放、状态识别、撤销、图片替换和主进程流程测试。

这些能力应在重构中保留。

## 发现与优先级

P1 表示建议优先进入下一批维护；P2 表示在边界稳定后完善。本次没有做攻击复现，下面的边界问题是实现上的不一致，不能据此直接推断已经发生安全事件。

### 1. P1：主进程包含浏览器运行时和大量服务逻辑

依据：[electron/main.cjs](../electron/main.cjs) 约 2,988 行，包含 24 个 IPC 处理器；从 [第 100 行](../electron/main.cjs#L100) 开始拼接用于网页的预览桥接脚本，同时还负责项目扫描、协议资源读取、快照、AI、文件写入和窗口生命周期。

影响：浏览器中的选中、拖动问题与桌面文件服务出现在同一文件里；修一个局部行为时，理解和回归范围过大。

修改：将可序列化的浏览器运行时提取到 `electron/preview/`，文件、快照和 AI 逻辑提取到独立服务，IPC 层只负责接收、校验、调用和返回。主入口最终只组装依赖、注册协议与创建窗口。不能把依赖 Node API 的代码直接序列化到网页。

### 2. P1：界面状态与操作集中在单一组件

依据：[src/App.tsx](../src/App.tsx) 约 1,642 行，包含 70 余处局部状态声明和 20 个 effect。`EditorView` 同时处理项目、预览、选区、撤销、保存、版本列表、AI 和多个面板。

影响：页面切换、保存、AI 预览和选区之间有较多状态联动，新增功能时容易漏清理或覆盖已有状态。

修改：先提取工具栏、预览区、属性面板、版本窗口和 AI 面板；再按职责提取状态 hook，统一处理页面切换和草稿状态。不一次性更换状态管理方案。

### 3. P1：文件保存方式没有统一

依据：[布局保存](../electron/main.cjs#L2602) 先备份，再直接 `writeFile` 覆盖入口文件；元素、背景、交互等保存存在同类路径。AI 应用则采用临时文件加 `rename`，见 [AI 应用](../electron/main.cjs#L2561)。

影响：不同保存入口对写入中断、外部修改和部分失败的处理不一致。创建了备份不代表当前文件写入一定完整。

修改：建立统一的保存服务，包含读入基线、内容校验、同目录临时文件替换、外部变更检查、项目级写入队列与失败清理。快照调用归入同一流程；多文件写回继续保留事务记录和失败恢复。Windows 文件占用和替换语义需要专项验证。

### 4. P1：路径与通信约束散落在各入口

依据：[resolveProjectFile](../electron/main.cjs#L1622) 检查路径字符串是否位于项目下；[真实路径检查](../electron/main.cjs#L1757) 在 AI 文件流程中使用，但普通保存和协议读取没有统一走这套检查。IPC 注册多处接收 `_event` 后直接校验 payload，缺少集中可审查的发送方校验；注入运行时主要依据消息中的 `source` 字段判断消息。

影响：不同入口对符号链接、目录联接、允许的发送窗口和消息格式采用不同规则，后续很难确认覆盖是否完整。

修改：文件服务统一检查真实目录边界；为新建文件检查其最近存在的父目录。IPC 统一核对窗口/顶层 frame 与参数结构；预览消息核对预期的 parent/source、页面会话与消息类型。保留已有隔离设置，明确外部导航与新窗口策略。

### 5. P2：通用编辑能力和特定素材适配混合

依据：[course-components.cjs](../electron/course-components.cjs) 内置一套购物篮素材哈希、节点与裁切比例；[scene-provider.cjs](../electron/scene-provider.cjs) 和 [svg-scene-layout.cjs](../electron/svg-scene-layout.cjs) 直接理解特定全局场景结构。

影响：跨画面能力对某种来源的依赖不容易从接口看出来，新增导出格式时可能继续往通用入口叠加特例。

修改：建立场景来源与组件识别的适配器接口，例如 `canHandle`、`getCurrentScene`、`listScenes`、`getComponentIdentity`。已有素材适配单独注册，并保留严格匹配条件和旧版保存兼容。无法对应时返回明确原因，不按位置猜测。

### 6. P2：跨进程类型与运行时校验没有共同来源

依据：界面类型位于 [App.tsx](../src/App.tsx)，桌面桥接声明位于 [electron.d.ts](../src/electron.d.ts)，实际接口位于 [preload.cjs](../electron/preload.cjs) 和主进程；部分复杂布局参数仍为 `unknown`。现有 TypeScript 配置主要覆盖 `src/` 和 Vite，未覆盖 Electron 的 CommonJS 实现。

影响：修改一处消息字段时，需要人工同步多个文件；界面类型正确也不能证明主进程收到的参数正确。

修改：在 `shared/` 中整理消息与保存模型，逐类建立运行时参数校验。保留 CommonJS 入口，先用 JSDoc 与分范围的 `checkJs` 扩大类型覆盖，避免同时迁移所有模块格式。

### 7. P2：已有测试依赖入口源码形状和外部素材

依据：[edit-scopes.test.cjs 第 14 行](../tests/edit-scopes.test.cjs#L14) 用正则从主入口提取脚本文本；[acceptance.test.cjs](../tests/acceptance.test.cjs#L69) 通过替换 `Module._load` 模拟 Electron；[check-image-selection.cjs](../scripts/check-image-selection.cjs) 包含特定项目的节点和操作流程。

影响：改文件布局可能破坏与行为无关的测试提取逻辑。公开仓库的维护者也没有本机真实课件可用于这些专项检查。

修改：预览脚本由显式工厂导出，服务通过参数注入 Electron/文件系统依赖。新增可公开的小型夹具覆盖 SVG ID、动态节点、裁剪和多状态；真实课件检查保留为可选参数。测试临时目录使用独立随机路径，统一关闭 watcher 后清理。

### 8. P2：缺少统一格式、自动检查与运行版本约定

依据：当前未配置 ESLint、格式检查、`.editorconfig`、`.gitattributes` 或 `.github/workflows/`；多项直接依赖使用 `latest`；未声明经过验证的 Node/npm 版本。已有 lockfile，所以 `npm ci` 并不等于每次自动更新依赖。

影响：成员使用不同换行或重新安装依赖时，可能产生大量无关差异；提交前检查依赖人工执行。

修改：先添加检查模式与 Windows CI，明确 Node/npm 版本并使用 `npm ci`。依赖版本从当前锁文件中经过验证的版本收敛，后续单独升级。格式化只覆盖新增和正在修改的模块，避免一次改写整个仓库。

### 9. P2：文档与发布流程仍偏内部维护记录

依据：[早期架构文档](02-technical-architecture.md) 仍写“当前仓库为空项目”；文档索引没有完整收录后续文档。发布辅助脚本在被忽略的 `release/` 中，源码获取者无法复用同一发布流程。窗口标题仍带历史“修复版”字样。

修改：首页描述用途与真实功能，更新记录描述用户可见变化；建立一份当前架构与兼容性说明，把早期需求标为历史。发布脚本放入 `scripts/release/`，把版本、校验、上传和发布结果作为可追踪步骤，凭据从执行环境读取。统一产品标题。

### 10. P2：公开仓库的维护入口不完整

依据：尚无 `LICENSE`、`CONTRIBUTING.md`、`SECURITY.md` 与问题模板。

修改：由维护者确定许可证，再补对应文件；贡献说明列出目录边界、开发命令和检查要求，问题模板要求版本、复现步骤和最小示例。`package.json` 的 `private: true` 是 npm 包发布设置，不是 GitHub 仓库可见性设置，无需因仓库公开而删除。

## 建议的目标结构

以下是分批迁移目标，不要求一次移动全部文件：

```text
electron/
  main.cjs                    应用组装与生命周期
  preload.cjs                 最小桌面 API
  main/                       窗口、协议和 IPC 注册
  services/                   项目、资源、保存、快照与 AI
  preview/                    浏览器运行时与注入脚本工厂
  adapters/                   场景来源与特定导出结构适配
src/
  app/                        应用外壳与项目切换
  features/
    project/                  项目与页面
    preview/                  设备、模式、定格与通信
    inspector/                文字、样式、交互与范围
    history/                  撤销与版本界面
    ai/                       设置、上下文、方案与差异
  components/                 通用按钮、对话框等
  styles/                     基础样式与功能样式
shared/                       消息契约、布局类型与校验
tests/
  unit/
  integration/
  fixtures/                   可公开的最小项目
scripts/
  dev/
  checks/
  maintenance/
  release/
docs/
  architecture/               当前架构与兼容约定
  guides/                     用户及开发指南
  history/                    历史需求与修复记录
```

## 分批实施安排

| 批次 | 具体交付 | 完成标准 |
| --- | --- | --- |
| 0：对外说明（本轮） | README、公开更新记录、已确认的 About/Release 文案与本审查计划 | 新用户能读懂用途、下载入口、功能边界；公开介绍不依赖内部课件编号。 |
| 1：基础约束与保存服务 | 明确运行版本、检查配置、Windows CI；提取路径处理、快照与写入服务；统一 IPC 发送方和参数校验 | 保存失败与外部变更有明确处理；真实路径边界统一；现有保存/恢复行为兼容。 |
| 2：拆分主进程与预览 | 提取窗口/协议/IPC、预览脚本工厂和 AI 服务；调整测试依赖注入 | 主入口只负责组装；预览模块可直接载入检查；保存到 HTML 的运行时及旧版记录继续兼容。 |
| 3：拆分界面与状态 | 提取预览区、工具栏、属性面板、版本与 AI；按功能管理状态和样式 | 页面切换、撤销、草稿保存和定格行为保持一致；功能组件无需读取整份编辑器状态。 |
| 4：适配器与公共夹具 | 提取特定素材适配，定义状态/组件接口，提供可公开示例 | 默认检查不依赖维护者盘符与私人素材；不同图层来源通过同一能力接口接入。 |
| 5：发布与贡献流程 | 发布脚本、干净环境打包、校验及发布清单；文档分区、贡献与许可证 | 从仓库可按说明构建安装包，发布可追溯；用户说明与内部维护记录有清楚入口。 |

## 每批回归要求

运行相应的单元与集成检查、界面类型检查和生产构建；涉及打包入口时检查打包后的程序。不能以“类型检查通过”代替实际编辑流程验证。

必须保留的行为：独立选中组件、拖动与缩放、撤销/重做、保存重开、动态节点重建、当前/指定/全部画面范围、设备范围、旧版保存记录、项目版本恢复。涉及 AI 时，另外检查隔离预览和失败恢复。

重构应按批次提交。文件移动与行为修复尽量分开；不批量改写用户项目、不更换保存标记或悄悄丢弃旧布局记录。
